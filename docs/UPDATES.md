# Обновления приложения из GitHub

Функциональная спецификация (ТЗ) для функции «обновление прямо из приложения».
Статус: **ТЗ утверждено, реализация — Sprint 09** (см. `ROADMAP.md`).

Связанные документы: `PRODUCT_SPEC.md` §5 (2.10), §7, §8; `INSTALL.md`;
`SECURITY.md`; `STATUS.md`.

---

## 1. Задача

Пользователь ставит Mellow вручную (APK из GitHub Actions) и не должен следить
за репозиторием сам. Приложение обязано:

1. само узнать, что вышла новая сборка;
2. **показать это внутри приложения** — заметным, но не навязчивым сообщением;
3. дать скачать новую версию прямо из приложения, с прогрессом;
4. после скачивания — предложить установку системным установщиком Android,
   сохранив данные (письма, аккаунты, токены, настройки).

Ключевой сценарий в одну фразу: *открыл приложение → сверху плашка
«Доступно обновление» → «Обновить» → полоса загрузки → «Установить» →
Android ставит новую версию поверх, ничего не потерялось.*

## 2. Термины

| Термин | Значение |
| --- | --- |
| Канал обновлений | Пара `owner/repo` на GitHub, откуда берутся сборки. Задаётся при сборке. |
| Сборка | Один APK, собранный CI, с известным коротким sha. |
| Проверка | Один запрос к GitHub, отвечающий «есть новее / нет / ошибка». |
| Установка | Передача скачанного APK системному установщику Android. |

## 3. Источник обновлений

### 3.1. Где берём данные

GitHub **Releases** того же репозитория, что и сборка:

```
GET https://api.github.com/repos/{owner}/{repo}/releases?per_page=10
```

> **Почему не `/releases/latest`:** этот эндпоинт отдаёт 404, если последний
> релиз помечен как pre-release или черновик. Именно так и случилось при первой
> публикации: CI создавал `--prerelease`, и `/releases/latest` отвечал 404,
> хотя APK был на месте. Поэтому: (1) CI публикует обычный релиз, (2)
> приложение всё равно читает **список** `/releases` и само выбирает первый
> подходящий — так одна ошибка в настройке релиза не отключает обновления
> целиком.

Ответ используется так:

| Поле | Как используем |
| --- | --- |
| `tag_name` | Идентификатор сборки, формат `build-<sha7>` |
| `name` | Человеческое имя: «Сборка 22f11d4» |
| `body` | Список изменений (Markdown), показываем как текст |
| `published_at` | Дата сборки, показываем «собрано 23 ноября» |
| `prerelease` | не фильтруем: если сборка помечена pre-release, она всё равно годится |
| `draft` | `true` → игнорируем |
| `assets[]` | Ищем файл `mellow-*-debug.apk`: `browser_download_url`, `size` |

**Как выбираем сборку из списка.** Список приходит от новых к старым по
`created_at`; берём первый элемент, который (а) не `draft`, (б) содержит
asset `mellow-*-debug.apk`. Если такого нет — переходим к §3.2.

Нельзя полагаться на порядок `published_at` и на «самый свежий по дате»:
GitHub ставит отметку «latest» по своим правилам, и на нашем репозитории она
уже один раз указала на более старую сборку (`build-9ca485a` вместо
`build-45163e0`). Порядок `created_at` в списке релизов стабилен, поэтому
сортируем по нему явно, а не доверяем `latest`.

Публичный репозиторий не требует токена. Для приватного (не наш случай)
предусмотрен заголовок `Authorization` из `--dart-define`; токен **никогда** не
пишется в логи и не показывается в UI.

### 3.2. Резервный источник

Если релизов нет (или API вернул 404), используется уже реализованный
`GET /repos/{repo}/commits?sha=main&per_page=1`. Тогда доступна только ссылка
на страницу Actions — без прямой загрузки. Это деградация, а не ошибка:
пользователь видит «Скачать вручную» и кнопку на страницу прогонов.

### 3.3. Как понимаем «новее»

Сравниваем **свой** короткий sha (`MELLOW_BUILD_SHA`, задаётся при сборке) с
sha из тега релиза:

* равны (или один — префикс другого) → обновления нет;
* отличаются → есть новая сборка;
* своя сборка без sha (локальная) → проверка сообщает «это локальная сборка,
  обновляться некуда» и не показывает плашку.

Версия `version:` из `pubspec.yaml` **не** используется для решения: она
меняется вручную и может отставать от кода. Semver применяется только для
отображения.

## 4. Когда проверяем

| Событие | Поведение |
| --- | --- |
| Старт приложения | Проверка через 3 с после первого кадра — не блокирует запуск |
| Возврат из фона | Проверка, если с прошлой прошло больше 6 часов |
| Экран «О приложении» | Кнопка «Проверить обновления» — всегда, без ограничений |
| Ручная установка | После успешной установки — сброс «отложено» |

Ограничения, чтобы не спамить и не жечь батарею:

* не чаще одного автоматического запроса в **6 часов** (метка в настройках);
* проверка **никогда** не запускается при отключённой настройке
  «Проверять обновления» (по умолчанию включена);
* проверка не блокирует интерфейс и не показывает ошибку, если сети нет:
  молчаливое «нет данных» вместо красной плашки;
* таймаут запроса — 10 с; при таймауте проверка считается неудачной.

## 5. Как показываем («выскакивает обновление»)

### 5.1. Плашка в списке диалогов

Тонкая полоса под верхней панелью, цвет `accentContainer`, не перекрывает
контент и прокручивается вместе со списком:

```
┌───────────────────────────────────────────────┐
│ ↑ Доступно обновление · сборка 22f11d4        │
│   Собрано 23 ноября  ·  [Обновить]  [Позже]   │
└───────────────────────────────────────────────┘
```

* **Обновить** → экран/лист «Обновление» с описанием изменений и кнопкой
  «Скачать (88 МБ)».
* **Позже** → плашка скрывается до следующего запуска (не навсегда).
* Крестик закрывает плашку на текущий запуск.

Плашка показывается **один раз за запуск** и только если обновление есть.

### 5.2. Локальное уведомление

Требование «чтобы показывалась уведомление, что пришло обновление»:

* если приложение в фоне и нашло обновление — системное уведомление
  «Доступно обновление Mellow» с текстом сборки, тап открывает приложение на
  листе обновления;
* уведомление об обновлении **не** зависит от настроек почтовых уведомлений
  (это не письмо) и не дублируется, пока обновление не установлено;
* канал уведомлений отдельный, пониженного приоритета (без звука).

Реализация уведомлений опирается на инфраструктуру Sprint 07; до неё плашка
в приложении остаётся обязательным минимумом, а уведомление — плюсом.

### 5.3. Экран «О приложении»

Обязательные элементы:

* текущая сборка: `22f11d4`, дата сборки, версия `0.3.0+3`;
* состояние проверки: «Проверяем…», «Установлена последняя сборка
  (проверено 12:40)», «Доступна сборка 22f11d4», «Не удалось проверить:
  нет связи»;
* кнопка «Проверить обновления»;
* при найденном обновлении — «Скачать» и «Что нового» (тело релиза);
* переключатель «Проверять обновления автоматически».

## 6. Скачивание

### 6.1. Процесс

1. Проверяем свободное место: нужно `размер APK + 50 МБ` запаса; если меньше —
   честное сообщение с указанием, сколько нужно освободить.
2. Скачиваем в `getTemporaryDirectory()/updates/mellow-<sha7>.apk` потоком,
   с прогрессом (получено/всего, проценты).
3. Проверяем целостность: размер совпадает с `assets[].size` из релиза; для
   APK — читается ли zip-заголовок (`PK\x03\x04`).
4. Кнопка «Отмена» прерывает загрузку и удаляет недокачанный файл.
5. Обрыв сети → «Продолжить» начинает заново (докачка по HTTP Range — плюс,
   но не обязательна для первой версии).

### 6.2. Ограничения

* одновременно не больше одной загрузки;
* загрузка не идёт по мобильной сети, если пользователь выключил
  «Скачивать по мобильной сети» (по умолчанию — можно);
* скачанный APK удаляется после успешной установки и при запуске, если он
  старше 7 дней.

## 7. Установка

### 7.1. Механика

* APK передаётся системному установщику через `FileProvider`
  (`open_filex` → `Intent.ACTION_VIEW` с `application/vnd.android.package-archive`).
* В манифесте объявляется `android.permission.REQUEST_INSTALL_PACKAGES`.
  Без него Android 8+ молча откажет в установке. Плагин `open_filex` это
  разрешение намеренно не запрашивает, поэтому оно добавляется нашим патчером
  `tool/platform/prepare_android.py`. Для Google Play это разрешение требует
  отдельного обоснования — мы распространяем APK вне Play, что и указано в
  документации.
* Пользователь подтверждает установку в системном диалоге. «Установить
  без сохранения данных» не предлагаем и не выполняем.

### 7.2. Требования к сборкам

Чтобы установка «поверх» работала, все сборки канала обязаны иметь:

| Требование | Почему |
| --- | --- |
| одинаковый `applicationId` (`app.mellow.mellow`) | иначе это другое приложение |
| одинаковый ключ подписи | иначе Android откажет «приложение не установлено» |
| `versionCode` не меньше предыдущего | откат версии Android не примет |

CI подписывает debug-сборки стандартным debug-ключом **раннера**; ключ
элементарен, но он должен быть стабильным. Поэтому вместо ключа из
`~/.android/debug.keystore` раннера используется ключ, сохранённый в секретах
репозитория (`MELLOW_KEYSTORE_BASE64`, `MELLOW_KEYSTORE_PASSWORD`), иначе
сборки с разных раннеров окажутся подписаны разными ключами. Пока секретов
нет — используется стандартный debug-ключ, а установка «поверх» может
потребовать удаления приложения; это состояние честно описано в `INSTALL.md`.

### 7.3. Если установка не удалась

Показываем причину и следующий шаг, без общих слов:

| Ситуация | Сообщение |
| --- | --- |
| Не выдано «Установка неизвестных приложений» | «Разрешите Mellow установку приложений в настройках Android» + кнопка в настройки |
| Другая подпись | «Сборка подписана другим ключом. Удалите Mellow и установите заново — данные будут потеряны» |
| Файл повреждён | «Скачайте заново» (сбрасывает файл) |
| Место кончилось | «Нужно ещё N МБ» |

Данные при штатной установке поверх сохраняются полностью: письма, контакты,
аккаунты, токены, настройки, тема, избранное.

## 8. Настройки

Новый раздел **Настройки → Обновления**:

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| Проверять обновления автоматически | вкл | старт и возврат из фона |
| Скачивать по мобильной сети | вкл | иначе только Wi-Fi |
| Показывать уведомление о новой сборке | вкл | системное уведомление |

Настройка «обновляться полностью автоматически, без подтверждения» **не
делается**: Android требует явного согласия пользователя на установку APK.
Обещать «само обновится» нельзя — это было бы ложью.

## 9. Безопасность

* Приложение скачивает APK **только** из релиза канала обновлений; URL берётся
  из API, а не из текста письма или ссылки в интерфейсе.
* Принимается только `https`, только хосты `api.github.com` (запрос списка),
  `github.com` (ссылка на файл) и те, куда GitHub перенаправляет сам файл:
  `objects.githubusercontent.com`, `release-assets.githubusercontent.com`.
  Список проверялся на живом релизе: `github.com/.../download/...` отдаёт 302
  на `objects.githubusercontent.com`, и это нормальный путь, а не подмена.
  Разрешённые хосты проверяются **после** каждого редиректа — клиент не должен
  слепо следовать за любым `Location`.
* Проверяется, что имя файла заканчивается на `.apk`, а размер совпадает с
  заявленным в релизе.
* Подпись APK проверяется системой при установке — приложение не может и не
  пытается это обойти. Свой APK приложение не устанавливает молча.
* Токен GitHub (если когда-нибудь понадобится для приватного репозитория)
  хранится в Keystore, никогда не попадает в логи, не показывается и не
  отправляется никуда, кроме `api.github.com`.

## 10. Ошибки и офлайн

| Сценарий | Поведение |
| --- | --- |
| Нет сети при проверке | молча: «нет данных»; в «О приложении» — «Не удалось проверить» |
| GitHub вернул 5xx | повтор через 30 с, максимум 2 попытки, потом тишина |
| GitHub rate limit (403) | «Слишком много проверок, попробуйте позже» |
| Нет релизов (404) | резервный путь по коммитам + ссылка на Actions |
| Обрыв во время загрузки | «Загрузка прервана», кнопка «Продолжить» |
| Обновление найдено, но оно старее текущего | не показываем; считаем «установлена последняя» |

## 11. Критерии приёмки

1. Сборка `A` установлена на телефон. Ветка получает новый коммит, CI
   публикует релиз `B`.
2. Открываем Mellow: **в течение ~5 секунд появляется плашка** «Доступно
   обновление».
3. «Обновить» → «Скачать»: виден прогресс, по завершении — «Установить».
4. Системный установщик ставит `B` поверх `A`, **все данные на месте**:
   аккаунты, письма, тема оформления, избранное.
5. В «О приложении» сборка сменилась на `B`, плашки нет.
6. Выключенная настройка «Проверять обновления» → плашка не появляется,
   запросов к GitHub нет.
7. Нет сети → приложение работает как обычно, ошибок не показывает.
8. Отказ в разрешении «установка неизвестных приложений» → понятное сообщение
   и кнопка в настройки, а не тишина.

## 12. Что НЕ делаем (и почему)

| Не делаем | Причина |
| --- | --- |
| Тихая установка без участия пользователя | Android требует согласия; на устройстве без root это невозможно |
| Свой сервер обновлений | противоречит §4 спецификации продукта: без своей инфраструктуры |
| Дельта-обновления | несовместимо с обычным APK и подписью; выгода не окупает риск |
| Откат на предыдущую версию | `versionCode` не позволяет; откат = удаление с потерей данных |
| Обновление по ссылке из письма/чата | прямой путь к подмене APK |
| iOS-обновления | вне возможностей без Apple Developer; только TestFlight, см. `INSTALL.md` |

# AGENTS.md — как работать над Mellow

Этот файл читается **первым** перед любой задачей. Он фиксирует правила, которые
не обсуждаются в рамках отдельного спринта: их изменение требует явного решения
человека.

---

## 1. Что за проект

Mellow — Flutter-приложение для iOS и Android, которое превращает обычную
электронную почту в диалоги. Mellow **не** почтовый сервер: он подключается к
Gmail, Яндекс Почте, Mail.ru, Outlook и произвольным IMAP/SMTP ящикам.

Текущий этап и точный объём работ — в [`docs/ROADMAP.md`](docs/ROADMAP.md).
Не начинай следующий спринт, пока предыдущий не закрыт по критериям раздела 9.

---

## 2. Железные правила

1. **Один модуль за раз.** Не переписывай полпроекта одним изменением.
2. **Сначала читай, потом пиши.** Перед правкой изучи существующие сущности,
   контракты и соседние фичи. Дублирование логики — дефект.
3. **Не меняй архитектурные решения без согласования.** Слои, DI, контракт
   `MailProvider` и схема БД — предмет договорённости, а не вкуса.
4. **Никаких фейковых реализаций вместо настоящей функциональности.** Если
   функция ещё не подключена, экран должен честно об этом сообщать, а не
   имитировать успех.
5. **UI, бизнес-логика и работа с почтой не смешиваются.** Виджет не знает про
   SMTP, репозиторий не знает про `BuildContext`.
6. **Каждая новая функция получает тесты.** Минимум: счастливый путь + граничный
   случай + случай ошибки.
7. **Секреты не пишутся в код, логи, тесты и документацию.** Ни токенов, ни
   паролей, ни реальных адресов почты в тестовых данных.
8. **После изменений:** `flutter analyze` и `flutter test` должны быть зелёными.
9. **Документация обновляется вместе с кодом.** Изменил схему — обнови
   `docs/DATABASE_SCHEMA.md`. Изменил контракт — обнови
   `docs/MAIL_PROVIDERS.md`.
10. **Локальное удаление ≠ удаление на сервере.** Ни одна операция «удалить»,
    «скрыть», «архивировать из вида» не должна вызывать удаление письма на
    сервере без явного действия пользователя.

## 3. Слои и направление зависимостей

```
presentation (features/*/presentation, core/widgets)
      ↓
application  (features/*/application — Riverpod-контроллеры)
      ↓
domain       (domain/entities, domain/repositories)
      ↑
data         (data/database, data/mappers, data/repositories)
      ↑
providers    (providers/contracts, providers/<adapter>)
```

* `domain/` **не импортирует** Flutter-материал, Drift, плагины, HTTP.
  Исключение — `package:flutter/foundation.dart` для `@immutable`.
* `data/` реализует контракты `domain/repositories`. Drift-типы (`*Row`,
  `*Companion`) не выходят за пределы `data/`.
* `providers/` — единственное место, где живут конкретные адаптеры почты и
  OAuth/PKCE. Токены сохраняются только через `SecureTokenStorage`.
* `features/` — фича владеет своими экранами, контроллерами и виджетами.
  Общий виджет живёт в `core/widgets` только если используется **двумя и более**
  фичами.

Проверка перед коммитом: если из `domain/` пришлось импортировать что-то из
`data/` или `features/` — решение неверное.

### 3.1. `services/` — прикладные движки вне фич

`lib/services/` (синхронизация, позже поиск и уведомления) занимает место между
`providers/` и `features/`: он координирует репозитории и адаптеры, но не рисует
UI. Правила для него:

* не импортирует `flutter/material` и ничего из `features/` — иначе движок
  нельзя запустить в фоновом isolate и протестировать без виджетов;
* зависит от `domain/` (контракты, сущности) и от `providers/contracts`;
* конкретные адаптеры выбираются фабрикой `providers/provider_factory.dart`,
  а не внутри сервиса.

`tool/check_structure.sh` проверяет и это правило: `lib/services/**` не должен
импортировать `flutter/material`, `flutter/widgets`, `flutter/cupertino` или
`features/`.

## 4. Правила по БД (Drift)

* Все первичные ключи — UUID Mellow. ID провайдера (`provider_message_id`,
  `provider_thread_id`) хранится отдельной колонкой и никогда не становится PK.
* Новая таблица = новая версия схемы + миграция в `MigrationStrategy`.
  Понижение версии запрещено.
* Уникальность — в схеме, не только в коде:
  * сообщение: `(account_id, provider_message_id)` + индекс по
    `messages.message_id_header`;
  * адрес контакта: `contact_emails.email` уникален глобально;
  * диалог: `(account_id, provider_thread_id)`.
* `*.g.dart` в git не хранится. После изменения таблиц:
  `dart run build_runner build --delete-conflicting-outputs`.
* Счётчики диалога (`unread_count`, `last_message_preview`, `updated_at`)
  пересчитываются только через `_refreshThreadCounters` в
  `DriftThreadRepository`, чтобы не разъезжались с содержимым.

## 5. Правила по контактам

* Email-адрес — идентификатор адресата, но **не** идентификатор человека.
* Автоматическое объединение по совпадению имени **запрещено**.
* Объединение двух адресов возможно только по явному действию пользователя
  (`ContactRepository.mergeContacts`).
* Автосоздание контакта при синхронизации — норма, но только по адресу.
  Имя берётся из заголовка `From`, иначе — эвристика `nameFromAddress`.
* Эвристика имени никогда не участвует в сопоставлении людей.

## 6. Правила по отправке и статусам

* Порядок: локальная запись → `queued` → `sending` → `sent` (сервер принял) или
  `failed`.
* `sent` **не** означает «прочитано». Не показывай двойные галочки как в
  мессенджере.
* Если результат отправки неизвестен (обрыв соединения), повторная отправка без
  сверки запрещена — это создаёт дубликат. Сначала сверка, потом решение.
* Черновик не теряется ни при ошибке провайдера, ни при закрытии экрана без
  подтверждения.

## 7. Правила по UI

* Цвета берутся только из `MellowColors` (через `MellowColors.of(context)`).
  Хардкод `Color(0x...)` в фичах запрещён.
* Отступы — из `MellowSpacing`, радиусы — из `MellowRadius`.
* Тёмная и светлая темы равноправны: любая новая поверхность проверяется в обеих.
* Текстовые стили — из `Theme.of(context).textTheme`; никаких фиксированных
  `fontSize`, ломающих системное масштабирование.
* Состояния экрана обязательны: загрузка, пусто, ошибка. Пустой список без
  объяснения — дефект.
* Все интерактивные элементы имеют семантическую подпись (tooltip/Semantics).

---

## 8. Правила по безопасности

* Токены OAuth — только в защищённом хранилище ОС, не в SQLite.
* Пароли приложений IMAP/SMTP — только в защищённом хранилище.
* HTML писем отображается только после санитизации, без внешних изображений и
  активного содержимого по умолчанию.
* Вложение открывается по MIME/расширению с белым списком; размер — в пределах
  лимита.
* Ошибки в UI не содержат тел писем и реквизитов доступа.

## 9. Критерии завершения задачи

Задача не считается выполненной, пока:

- [ ] функциональность реализована полностью в заявленном объёме;
- [ ] `flutter analyze` без ошибок и предупреждений;
- [ ] `flutter test` проходит, новые тесты добавлены;
- [ ] не сломаны существующие сценарии (ручной прогон затронутых экранов);
- [ ] обработаны ошибки и граничные случаи (пусто, офлайн, дубликат, отмена);
- [ ] документация обновлена, если изменились архитектура, схема или контракты;
- [ ] в отчёте перечислено, что осталось за рамками задачи.

## 10. Команды

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # после правок схемы
flutter analyze
flutter test
flutter test test/data/drift_repositories_test.dart        # один файл
bash tool/check_structure.sh   # правила слоёв, работает без Dart SDK
flutter run                                                # демо-данные в debug
flutter run --dart-define=MELLOW_DEMO_SEED=true            # демо и в release
```
